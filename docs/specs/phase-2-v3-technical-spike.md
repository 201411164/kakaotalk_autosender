# Phase 2 — V3 기술 검증 Spike 계획

**목적:** V3 “멀티 PC 카카오 작업대”의 핵심 UI가 실제 Win32/Windows 자동화로 구현 가능한지 먼저 확인합니다.  
**범위:** 새 톡, 미등록 톡방, 개인톡, 현재 화면 캡처, 톡방 열기/보내기 명령의 기술 가능성 검증  
**상태:** Spike 1 읽기/캡처 도구 추가됨  
**원칙:** 카카오톡 실발송은 사용자 승인 전 수행하지 않음. 발송 관련 검증은 우선 DRY_RUN 또는 테스트 방 1개로 제한.

---

## 1. 왜 Spike가 먼저 필요한가

수정 기획안의 핵심은 “PC 상태 대시보드”가 아니라 **선택한 PC의 카카오톡 작업 화면**입니다.

그런데 현재 코드가 확실히 제공하는 기능은 다음 수준입니다.

| 기능 | 현재 코드 근거 | 신뢰도 |
|------|----------------|--------|
| 카카오톡 메인 창 찾기 | `win32gui.FindWindow(None, "카카오톡")` | 중 |
| 채팅방 검색 후 열기 | `open_chat(room_name)` | 중 |
| 열린 대화창 제목 감지 | `list_open_kakao_chats()` | 중 |
| 텍스트 발송 | `send_text(room_name, text)` | 중 |
| 이미지 발송 | `send_image(room_name, image_path)` | 중 |
| DRY_RUN | `config.is_dry_run()` | 높음 |

반면 V3 UI가 요구하는 아래 기능은 현재 코드에 없습니다.

- 새 톡 개수 감지
- 미등록 톡방/개인톡 자동 감지
- 최근 메시지 미리보기
- 선택 PC의 카카오톡 화면 캡처
- 원격 명령 큐를 통한 “열기 / 등록 / 보내기 / 발송 중지”

따라서 UI 구현 전에 “가능한 것 / 제한적인 것 / 포기하거나 UX를 바꿔야 하는 것”을 확인해야 합니다.

## 3. 현 코드 기준 1차 판정

### S1. 카카오톡 실행 여부

**현재 가능성:** 높음

근거:

- `check_kakao_running()`이 `FindWindow(None, "카카오톡")`로 메인 창 존재 여부 확인.
- V3 Agent에서도 같은 방식으로 1차 상태 보고 가능.

주의:

- 카카오톡 창 제목이 언어/버전에 따라 바뀌면 실패 가능.
- 트레이에만 있고 메인 창이 숨겨진 경우 감지가 불안정할 수 있음.

판정:

- MVP 가능.
- 단, “카카오 실행 중”은 “메인 창 감지됨” 기준으로 문구를 정의해야 함.

---

### S2. 열린 대화창 목록 수집

**현재 가능성:** 중간

근거:

- `list_open_kakao_chats()`가 전체 윈도우를 순회하면서 `RICHEDIT50W` 입력창이 있는 창 제목을 대화창으로 판단.
- 현재 V2의 “현재 열린 채팅방 추가” 기능에서 이미 사용.

제약:

- “열려 있는 창”만 감지 가능.
- 카카오톡 메인 목록에 보이는 모든 톡방을 수집하는 기능은 아님.
- 새 톡/미등록 톡방 전체 감지와는 별개.

판정:

- MVP에서 “현재 열린 톡방” 감지로는 사용 가능.
- “등록된 톡방 전체 상태”를 의미하게 하면 안 됨.

---

### S3. 새 톡 개수 감지

**현재 가능성:** 불확실

가능한 접근:

1. **UI Automation / pywinauto로 카카오톡 메인 목록 접근**
   - 장점: 텍스트/배지 접근 가능성이 있음.
   - 단점: 카카오톡 UI가 custom control이면 읽기 어려울 수 있음.

2. **스크린샷 + OCR/이미지 인식**
   - 장점: UI Automation이 안 될 때 대안.
   - 단점: 정확도·성능·폰트/해상도 의존, 구현 복잡.

3. **알림/윈도우 타이틀 기반**
   - 장점: 구현 단순.
   - 단점: 방별 새 톡 수는 거의 불가능.

판정:

- MVP 전에 반드시 프로토타입 필요.
- 안정적으로 안 되면 UI 문구를 “새 톡 감지됨”이 아니라 “확인 필요 톡방” 또는 “최근 열린 톡방”으로 낮춰야 함.

---

### S4. 등록/미등록 톡방 구분

**현재 가능성:** 조건부 가능

구현 아이디어:

- 등록 톡방: 로컬/Hub에 저장된 `registered_rooms`
- 감지 톡방: Agent가 수집한 `detected_rooms`
- 미등록 톡방: `detected_rooms - registered_rooms`

전제:

- Agent가 어떤 방식으로든 `detected_rooms`를 수집해야 함.
- 현재 코드의 `list_open_kakao_chats()`는 “열려 있는 대화창”만 제공하므로 범위가 좁음.

판정:

- “열려 있는 미등록 톡방”은 가능.
- “카카오 목록 전체의 미등록 톡방”은 S3/S6 결과에 의존.

---

### S5. 개인톡 구분

**현재 가능성:** 낮음~불확실

문제:

- 카카오톡 창 제목만으로 개인톡/단체방/오픈채팅을 안정적으로 구분하기 어려움.
- 이름이 사람 이름처럼 보인다고 개인톡이라고 판단하면 오탐 가능.

가능한 정책:

1. 자동 구분하지 않고 **“미등록 톡방”**으로만 표시
2. 사용자가 등록 팝업에서 `개인톡 / 단체방 / 고객상담` 분류 선택
3. 카카오 UI Automation에서 참여자 수 등의 정보가 읽히면 개인톡 추정

권장:

- MVP에서는 자동 개인톡 판정을 강하게 쓰지 말고, **“미등록 톡방” 기본 + 사용자가 개인톡으로 분류**.

---

### S6. 최근 메시지 미리보기

**현재 가능성:** 불확실

가능한 접근:

1. UI Automation으로 목록의 마지막 메시지 텍스트 접근
2. 창을 열고 화면/클립보드 방식으로 마지막 메시지 읽기
3. OCR

리스크:

- 개인정보 노출
- UI 변경 취약
- 읽기 자동화가 발송 자동화보다 훨씬 불안정할 수 있음

권장:

- MVP UI는 “미리보기”를 옵션으로 두고, 실패 시 `새 메시지 있음` 또는 `내용 숨김`으로 대체.
- 개인톡은 기본 미리보기 숨김.

---

### S7. 현재 화면 캡처

**현재 가능성:** 중~높음

가능한 접근:

1. `win32gui`로 카카오톡 창 핸들 찾기
2. `PrintWindow` 또는 `ImageGrab.grab(bbox=...)`로 캡처
3. Hub로 이미지 업로드 또는 Console에서 요청 시 직접 표시

주의:

- 최소화된 창은 캡처가 검게 나오거나 실패할 수 있음.
- 개인톡 내용이 포함될 수 있으므로 보안 정책 필요.

판정:

- MVP에서 가장 먼저 검증할 가치가 큼.
- UI의 “현재 화면” 탭은 기술적으로 현실성이 있음.

---

### S7-1. 1초 단위 캡처 스트림

**현재 가능성:** 중~높음

Spike 결과:

- DPI 보정 + `PrintWindow` 방식으로 대화창 전체 캡처 성공.
- 캡처 이미지는 이전 대화와 현재 화면을 사람이 확인하는 용도로 충분한 가능성이 있음.

권장 동작:

- 선택 PC 1대만 1초 단위 캡처.
- 메시지 보내기 후 T+1초에 자동 캡처.
- 이후 사용자가 해당 PC를 보고 있는 동안 1초 단위 갱신 유지.
- 다른 PC로 선택 변경 시 이전 PC 스트림 중지.

부하/보안 고려:

- 모든 PC를 1초마다 캡처하면 5~10대 환경에서 네트워크·CPU·개인정보 부담이 큼.
- 전송 포맷은 PNG보다 JPEG/WebP 압축을 검토.
- Hub에는 기본적으로 최신 프레임만 유지하고 영구 저장하지 않음.

판정:

- V3 MVP에 “현재 화면 1초 자동 갱신” 포함 가능.
- 구현 전 60초 연속 캡처 부하 측정 Spike 필요.

---

### S8. 원격 `열기` 명령

**현재 가능성:** 중

근거:

- 기존 `open_chat(room_name)` 재사용 가능.

주의:

- 정확한 방 이름 필요.
- 명령 실행 시 해당 PC의 카카오톡 UI 포커스가 바뀜.

판정:

- MVP 가능 후보.
- 사용자에게 “열기”는 해당 PC 카카오톡 화면을 바꿀 수 있음을 알려야 함.

---

### S9. 원격 `보내기` 명령

**현재 가능성:** 기술적으로 가능, 운영 위험 높음

근거:

- `send_text`, `send_image`, `MessageSenderThread` 존재.
- DRY_RUN도 구현되어 있음.

리스크:

- 잘못된 PC/톡방으로 실발송 가능.
- Console에서 보낼 경우 운영자 확인 UX가 필수.

권장:

- Spike는 **DRY_RUN → 테스트 방 1건 → 제한 승인** 순서.
- MVP에 포함하더라도 기본은 “보내기 전 확인 모달” 필수.

---

### S10. 발송 중지

**현재 가능성:** 현재 구조에서는 제한적

근거:

- 랜덤 발송은 `stop_random_sending()`으로 타이머 중지 가능.
- 이미 실행 중인 `MessageSenderThread.run()` 내부 루프는 중지 플래그가 없음.

문제:

- 여러 방 일괄 발송 중 즉시 중지하려면 스레드에 `cancel_requested` 같은 플래그가 필요.

판정:

- “랜덤 발송 중지”는 가능.
- “현재 일괄 발송 즉시 중지”는 코드 개선 필요.

- 없음

---

목표:

- 카카오톡 메인 목록에서 방 이름·새 톡 수·최근 메시지 preview를 읽을 수 있는지 확인
- UI Automation / pywinauto / OCR 후보 비교

산출:

- 방식별 성공/실패 표

실발송:

- 없음

---

### Spike 3 — 미등록 톡방 구분

목표:

- 등록 톡방 목록과 감지 톡방 목록을 비교해 미등록 톡방을 만들 수 있는지 확인
- 개인톡 자동 구분 가능성 확인

산출:

- `registered_rooms`, `detected_rooms`, `unregistered_rooms` 예시 JSON
- 개인톡 분류 정책

실발송:

- 없음

---

### Spike 4 — 제한 명령

목표:

- `열기`
- `현재 화면 새로고침`

---

### Spike 5 — 1초 캡처 스트림 부하 측정

목표:

- 선택한 대화창을 60초 동안 1초 단위로 캡처
- 평균 캡처 시간, 이미지 크기, 실패 횟수 측정

산출:

- 평균 캡처 latency
- 1분 총 데이터 크기
- CPU 체감 부하
- V3 Agent 기본 캡처 주기 권장값

실발송:

- 없음

산출:

- 명령별 성공/실패 조건
- Console UX 확인 모달 요구사항

실발송:

- 기본 없음
- 사용자가 승인한 테스트 방 1개만 별도

1. **MVP에서 가장 현실적인 기능**
